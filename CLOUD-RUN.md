# Облачные запуски LifeMart

Ежедневный боевой исполнитель `LifeMart production pass` работает на сервере GitHub,
независимо от компьютера, приложения Codex и этого чата.

| Екатеринбург | Слоты отправки | Cron UTC |
|---|---|---|
| 08:30 | 09:00, 10:00 | `30 3 * * *` |
| 10:30 | 11:00, 12:00, 13:00 | `30 5 * * *` |
| 14:00 | 15:00, 16:00 | `0 9 * * *` |

Все три расписания ежедневные, включая выходные. На событии `schedule` автоматически
выбираются нужные слоты и режим `apply`. Ручной запуск по умолчанию остаётся `preview`.
Последовательность АВ12 → М42 → Г34; одновременные боевые проходы запрещены concurrency.
Локальный исполнитель должен оставаться отключённым. Журнал и ошибки доступны в
[GitHub Actions](https://github.com/SergeyMartynov96/JmRabotaOblako/actions/workflows/cloud-production.yml).

GitHub не гарантирует точность времени cron. Если задание опоздало до первого слота
отправки, оно завершается ошибкой и требует сверки истории СУ; отсутствие ожидающих
карточек после опоздания не маскируется успешным пустым проходом. До дедлайна пустое
ежедневное окно считается штатным отсутствием работы. При частичном сбое сохранённые
отпечатки защищают уже изменённые карточки от нового сокращения при повторе.
Первое фактическое срабатывание ежедневного расписания ещё предстоит проверить.

Его устаревший cron удалён: теперь этот тест доступен только вручную. Ежедневное
боевое расписание находится в отдельном `cloud-production.yml` и остаётся активным.
Наблюдавшаяся задержка 6 ч 38 мин показывает, что GitHub cron нельзя считать

опоздании остановится с ошибкой и потребует сверки уже отправленных заявок.

Задание доступно также вручную в GitHub → Actions → LifeMart cloud read-only test → Run workflow.
Параметр `slots` задаёт время отправки заявок по Екатеринбургу; для теста 14:00 — `15:00,16:00`.

Задание входит в СУ, проверяет доступ к трём филиалам и таблицам, читает актуальные
заявки, оформленные в день запуска, и сверяет суммы карточек с таблицами по дате привоза.
Карточки поставщиков вне заголовков таблицы не открываются. Неоднозначные соответствия
пропускаются. Если отчёт требует пагинации, проверка завершается ошибкой вместо
выдачи частичного результата. Если подходящих карточек нет, функциональный тест
не считается пройденным. Уже отправленные заявки это задание не восстанавливает:
при задержке старта за время отправки нужна отдельная сверка истории.

**Это тест чтения и расчёта текущих сумм, а не боевой алгоритм корректировки.**
CSV не различает формулы плана и факты: исходный план до прежних правок не восстанавливается.
Скрипт не меняет заявки, таблицы или расписания СУ. Публикация среды Codex для этого
задания не нужна.

Учётные данные передаются только через GitHub Actions Secrets
`LIFEMART_LOGIN` и `LIFEMART_PASSWORD`. Чтение доступов из
`AGENTS.md` удалено; при отсутствии секретов запуск безопасно останавливается.
Секретные значения не включены в скрипт и маскируются перед сетевыми запросами.
В общедоступный журнал выводятся только результаты доступа и количество проверенных
и пропущенных заявок, без финансовых сумм, ID заявок и имён поставщиков.

Локальная проверка:

```sh
python3 -m unittest discover -s tests -v
python3 scripts/cloud_readonly_test.py --slots '15:00,16:00'
```

Для подробного локального отчёта можно передать `--report /tmp/lifemart-check.json`.
Он содержит рабочие данные: не добавлять его в Git или общедоступные артефакты Actions.
Пакеты сторонних библиотек не требуются; используются Python 3.9+ и системная проверка TLS.


## Боевой исполнитель

`LifeMart production pass` (`.github/workflows/cloud-production.yml`) запускается
ежедневно по расписанию выше и вручную через GitHub Actions. `operation=preview` выполняет полный расчёт без
сохранения; `operation=apply` повторяет расчёт, сохраняет контрольные отпечатки
и только затем применяет изменения. Слоты задаются параметром `slots` по Екатеринбургу.
Ежедневное расписание включено; `scripts/cloud_schedule.py` выбирает слоты по cron-событию.
Локальный исполнитель остаётся отключённым.

Порядок АВ12 → М42 → Г34. АВ12 переносит факты без изменения заявок.
М42 и Г34 читают плановую формулу и рассчитанное значение из одного листа,
учитывают топы, исходные количества, кратность и минимумы. Уже записанное число
принимается как факт только при совпадении с полным итогом карточек.
Количество 1 и 2 сохраняется; при недостижимой цели ассортимент не обнуляется.
Г34 контролируется по независимой сумме поставщиков с пределом 60 000 ₽;
мягкий ориентир М42 допускает превышение до 2 000 ₽ согласно §6 регламента.
Табличные дневные итоговые формулы сохраняются.

Перед сохранением проверяются все актуальные заявки поставщика по дате привоза,
включая отправленные; изменяются только ожидающие заявки выбранных слотов.
Смена состава группы, неоднозначная ячейка, неизвестная форма, изменившаяся карточка,
пагинация или отсутствие подтверждённого плана останавливают зависимую операцию.
После второго шага сохранения карточка перечитывается, и только подтверждённый
агрегированный факт записывается в исходную ячейку. Запись проверяется через CSV
и строку формул. В публичный журнал не выводятся суммы, поставщики или ID карточек.

До изменений Actions сохраняет артефакт `lifemart-journal-<run_id>` с SHA-256
отпечатками исходных и желаемых карточек, без количеств, цен и сумм. Полный
рабочий план остаётся временным файлом runner и удаляется при завершении. При
повторном запуске прежние отпечатки загружаются: сохранённая карточка не сокращается
повторно, после сбоя записи таблицы повторяется перенос. Если состояние не совпадает
ни с исходным, ни с ожидаемым, требуется отдельная сверка. Артефакты хранятся 90 дней.
Обычный повтор выполняется новым `Run workflow`, а не перезапуском только последнего
шага; два боевых задания одновременно не выполняются. При частичном сбое сначала
сверить сохранённые карточки и ячейки, затем запускать оставшееся окно.

Проверка 08.11.2026: [предварительный проход](https://github.com/SergeyMartynov96/JmRabotaOblako/actions/runs/42466944724)
и [боевой проход](https://github.com/SergeyMartynov96/JmRabotaOblako/actions/runs/42467181066)
успешны. Окно 15:00/16:00: подтверждены 5 фактических ячеек, изменена одна заявка
М42; АВ12 и Г34 перенесены без изменения количеств. Пропусков поставщиков в этом
окне не было. Это проверка данного окна, а не подтверждение ежедневного расписания.

[Повторный расчёт после боевого прохода](https://github.com/SergeyMartynov96/JmRabotaOblako/actions/runs/42467478725)
успешно загрузил контрольный журнал и предложил **0 изменений** по всем филиалам.
Пять фактических ячеек дополнительно сверены независимым HTTPS-чтением СУ и CSV.


## Бесплатный внешний таймер — подключён и проверен

После фактической задержки GitHub cron на 6 ч 38 мин основной запуск перенесён
в [cron-job.org](https://cron-job.org/en/), GitHub cron оставлен резервом. Сервис бесплатен;
GitHub-hosted исполнение в этом публичном репозитории также не требует отдельного VPS.
Своевременность бесплатных сервисов не гарантирована: остаётся риск очереди runner GitHub.
Это устранение обнаруженной задержки генерации cron-события, а не обещание абсолютного SLA.
Платный Railway не выбран: пользователь требует отсутствие ежемесячной оплаты.

Готовые шаблоны трёх заданий выдаёт `python3 scripts/external_cron_config.py`. Они
создаются выключенными и не содержат действительных ключей. Метод POST, URL
`https://api.github.com/repos/SergeyMartynov96/JmRabotaOblako/actions/workflows/cloud-production.yml/dispatches`.
В заголовке Authorization нужен отдельный fine-grained GitHub token только для этого
репозитория с Actions: read/write. Хранить ключ в защищённых настройках задания,
не в репозитории и не в чате. Пароль СУ внешнему таймеру не передаётся.

| Задание | Вызовы по Екатеринбургу | `external_window` |
|---|---|---|
| Утро | 08:30, 08:35, 08:40, 08:45, 08:50 | `morning` |
| День | 10:30, 10:35, 10:40, 10:45, 10:50 | `midday` |
| После обеда | каждые 5 минут с 14:00 по 14:50 | `afternoon` |

Тело: `{"ref":"main","inputs":{"operation":"apply","external_window":"morning"}}`;
для других окон заменить `external_window`. Слоты и дедлайн назначаются кодом.
Повторные вызовы нужны на случай сбоя первого прохода. После успеха сохраняется
нефинансовый артефакт `lifemart-complete-<дата>-<окно>`. Повторный вызов и поздний
резервный GitHub cron проверяют артефакт и успешный статус того же workflow в main,
а затем пропускают работу. Один принятый HTTP 204 означает только принятие запроса
GitHub, не завершение закупки. Новый день имеет другой ключ. Ошибки чтения журнала
не считаются признаком успешно завершённого окна. Старые и преждевременные события
отсекаются по дате создания run, началу окна и дедлайну.

Независимый контроль подключён через Cronitor (раздел ниже). Healthchecks был
первоначальным вариантом, но регистрация не завершилась из-за недоставленных писем.
Суммы, поставщики и ID заявок в монитор не отправляются. Старые переменные
`HEALTHCHECK_*` сохранены в коде лишь как совместимый запасной вариант.

Аккаунт cron-job.org подключён через API. Отдельный GitHub dispatch-token установлен
в защищённые HTTP-заголовки заданий; все три задания включены и перечитаны.

тесты и проверку конфигурации без обращения к СУ и таблицам. Внешняя доставка проверена одноразовым заданием `verify` с `external_window=none`:

завершения должно привести к нарушению расписания к 08:45/10:45/14:15, с учётом
частоты оценки бесплатного сервиса. Полная недоступность GitHub также оставит pulse
неполученным. Получение HTTP 200 от telemetry не считается достаточной проверкой:
нужно перечитать состояние монитора и проверить канал уведомлений.

Для runtime используется только ключ Telemetry, хранящийся в GitHub Actions Secret
`CRONITOR_TELEMETRY_KEY`. Управляющий ключ LifeMart нужен для настройки через API;
SDK-ключ с полным доступом не используется. Ключи не сохраняются в Git.
Режим `operation=monitor-verify` отправляет три пробных сигнала в окружение
`setup-test`, пропуская все шаги чтения/изменения СУ и таблиц. Обычный `verify`
по-прежнему выполняет только проверки конфигурации. Production pulse формируется
только после успешного сохранения и проверки фактов либо по успешной квитанции
того же окна. В pulse нет имён поставщиков, сумм или ID заявок.

Три production-монитора включены: paused=false, initialized=true, passing=true.
Владелец сохранил Telemetry key в GitHub Secret. [Проверка доставки из GitHub
42503359139](https://github.com/SergeyMartynov96/JmRabotaOblako/actions/runs/42503359139)
успешна: все 33 теста прошли, шаги СУ и таблиц пропущены, новые setup-test события
перечитаны через API Cronitor по времени после начала run. У setup-test выключены
уведомления (with_alerts=false), у production они включены. Перед первым рабочим
окном production инициализирован событием state=ok: это настройка мониторинга,
а не запись об исполненной закупке. Первый регулярный бизнес-проход ещё предстоит.

Канал default содержит один адрес аккаунта. Отдельный `lifemart-delivery-test`

(passing=true) и поставлен на паузу (paused=true), чтобы не рассылать новые тревоги.
Три рабочих монитора перечитаны и остались активными и здоровыми. Всего четыре

лимита пяти. Данные закупок во всех проверках мониторинга не менялись.

### Восстановление пропущенного окна

Ручная операция `recover` принимает слоты, например `09:00,10:00` после 09:00.
Она привязана к дате создания запуска и заканчивается перед ближайшим ещё будущим
слотом. Отправленные сегодня заявки сверяются и переносятся только как факты;
ожидающие с истёкшим слотом также не редактируются. Отменённые не выбираются.
При external_window=none режим не создаёт квитанцию планового окна и не отправляет его heartbeat.
При явном external_window=morning/midday/afternoon проверяется полный набор слотов
этого окна; только после успешной сверки и записи разрешены квитанция и heartbeat.

Расчёт сокращений не использует фиксированные процентные нижние пороги.
Сохраняются единицы, двойки, кратность, минимумы СУ и приоритет топов.
При превышении дневного предела остаток перераспределяется только между
доступными заявками готовой еды/Японии: не ниже 95% плана поставщика,
без изменений отправленных и исходно меньших плана заявок. Если допустимого
варианта нет, preflight останавливается до любых сохранений.
