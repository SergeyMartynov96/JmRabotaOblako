# Личные отчёты Telegram

Бот `@JmReport1_bot`; токен только в Actions Secret `TELEGRAM_BOT_TOKEN`.
Личный получатель проверен одноразовым Start-кодом; в репозитории хранится только
AES-GCM-привязка, ключ которой выводится из токена бота. Сырые chat_id, cookies,
исходные финансовые данные и изображения в публичные журналы не выводятся.

`telegram-reports.yml`: `preview` собирает изображения для зашифрованного просмотра;
`deliver` собирает все выбранные филиалы и отправляет каждому один альбом из восьми
изображений в один проверенный личный чат. `verify` проверяет токен/привязку без сообщений.
Начало подписи — АВ12, М42 или Г34, затем согласованные восемь пунктов.

1. Недельный блок исходной «Выручки», экспорт PDF → PNG с форматированием Sheets.
2. Последний поставщик приходных накладных, получатель и три суммы. Фильтр —
   дата приёма вчера, подразделение получения товара, 23 утверждённых контрагента.
3. Нативная таблица причин списаний за вчера.
4. ТОП списаний: штуки и рубли рядом, по убыванию каждого показателя.
5. % списаний по дням + УИ2, по убыванию суммы списаний в рублях.
6. УВ по блюдам, 200 записей на странице, первый экран полноэкранной таблицы.
7. УВ по стоп-статусам по дням, Grouped.
8. Четыре графика OSA по матрице магазина; нативная легенда отключает 17:00,
   «вечер» и «утро». В подписи — вчерашние 11:00 и 20:00 «Готовая еда + Япония».

Для УИ2/УВ/OSA — понедельник текущей недели → начало сегодняшнего дня,
гранулярность день. В понедельник — предыдущий понедельник → текущий понедельник.
Накладные, причины и ТОП списаний — только вчера. Правая граница BI исключена.
Сервер BI должен подтвердить применение филиального фильтра и точные границы.
Изображения BI создаются собственными рендерами Superset из проверенного результата;
повторный запрос данных при отрисовке заменяется уже полученным результатом.
При отсутствии сохранённого query_context запрос строит тот же плагин Superset,
а выполнение блокируется до применения нужного филиала и дат.

Подготовка сессии использует проверенный HTTP-вход СУ с переносом cookies в Chrome.
BI использует ранее проверенный accounting-переход и CSRF из DOM, без ожидания
всего дашборда. На запрос данных и отрисовку отдельного графика — до 180 секунд.
Снимок ждёт окончания JavaScript-анимаций. Ошибка/пустой результат не становятся
нулём или изображением загрузки. Во время сборки таблицы и документы не изменяются.

Перед попыткой отправки создаётся минимальная квитанция даты/филиала; квитанции
публикуются без финансовых данных. Повторная попытка того же дня подавляется даже
при неоднозначной сетевой ошибке Telegram. Автоматического повторного send нет.
Исходные PNG и диагностический JSON покидают runner только внутри зашифрованного
RSA-OAEP/AES-GCM пакета для визуальной проверки либо в проверенный личный Telegram.

Расписание: `telegram-report-timer.yml` реагирует на запрос существующего внешнего
утреннего `LifeMart daily metrics` apply/all в 08:00–08:30 Екатеринбурга. Отдельный
job ждёт 09:00 и делает dispatch deliver/all, независимо от результата таблиц.
Оригинальный workflow таблиц не меняется. Сигналы другой даты, ветки, репозитория,
операции и окна отвергаются; после 09:15 опоздавший dispatch запрещён. Ручной запуск
таймера проверяет связку dispatch → verify, без рассылки и ожидания 09:00.
Первый плановый запуск этой цепочки ещё требует проверки; успешная ручная доставка
не доказывает своевременность будущего внешнего сигнала и очереди GitHub.
